# 护轨扩展：按提供图片实现

实现范围为图片中清晰可读的第 1、3、4、5 项。第 2 项被模糊处理，没有猜测或补写其需求。

| 图片要求 | 实现位置与行为 |
| --- | --- |
| 智能敏感词检测 | `LlmPromptReviewer` 使用独立、无记忆、无工具的审核调用，识别语义风险；先执行本地快速检查与凭据脱敏，再把本轮正文、附件提取文字和选中元素送审。选择了图片允许的“调用专门 AI 模型”方案，没有增加阿里云服务依赖 |
| Prompt 重写 | `PromptSafetyInputGuardrail.prepare` 返回通过、重写或拦截结果。只允许移除原文中精确匹配的越权片段、或替换为固定脱敏占位符；不接受审核模型新增功能或输出任意改写指令。语义重写后再审一次，仍有风险则拒绝，不循环重试 |
| 定制错误反馈 | `GlobalExceptionHandler` 处理连接建立前的异常；`AppController` 处理异步及 SDK 包装异常。SSE 返回 `business-error` 和 `done`，包含错误码、用户说明、规则编号及审计参考编号；前端停止流并展示说明和参考编号。重写通过时通过现有 `progress` 事件显示“安全检查” |
| 审计记录 | `APPFORGE_GUARDRAIL_AUDIT` 输出结构化 JSON 日志，记录所有重写、拦截、审核失败的时间、用户 ID、应用 ID、来源、命中规则、处理结果与 requestId；另记录输入/输出长度及 SHA-256 摘要。正常放行不额外记录日志 |

## 接入位置

- 创建应用：在智能路由和保存应用之前审核；重写后的初始需求用于路由、名称和数据库保存。
- 聊天生成：先校验应用和附件归属，拼接选中元素及附件文字，再审核；审核通过后才认领生成任务、保存用户消息或调用代码生成模型。三种代码生成模式共用此入口。
- SDK 兼容入口：保留 InputGuardrail 接口，支持 `successWith` 把本地重写传给 SDK；异常保留受控原因。手工构造的 SDK 兼容适配器只进行本地检查；实际应用入口使用 Spring 注入的完整语义审核器。
- 用户消息最多 2000 字；附件及元素上下文单独限长，默认 80000 字。超过限制会明确报错，不在护轨内静默截断。原有附件提取流程自身的截断规则保留。
- 审核运行在现有 boundedElastic 调度器上；客户端取消后，审核返回也不会继续启动生成。

## 模型与配置

默认开启语义审核。未单独配置时，审核器读取已有 `langchain4j.open-ai.chat-model` 的地址、密钥与模型名，使用独立客户端；不修改生成、路由或推理模型的 Bean。审核请求禁用请求/响应日志、工具和会话记忆，使用 JSON 输出与非思考模式，最多输出 2048 tokens，默认 15 秒超时，不自动重试。

每次正常请求增加一次审核调用；需要语义重写时最多两次，因此会增加模型调用费用和等待时间。请求模型失败、超时或返回不合法 JSON 时，返回 `50310`“安全检测暂不可用”，不会当作通过。

可按需在 `application.yml` 中添加以下配置（若已有 `appforge` 节点，合并到该节点内）：

```yaml
appforge:
  guardrail:
    semantic-enabled: ${APPFORGE_GUARDRAIL_SEMANTIC_ENABLED:true}
    timeout-seconds: 15
    max-context-chars: 80000
    # 下列三项留空时复用 chat-model；如使用专门的审核模型，可单独设置。
    base-url: ${APPFORGE_GUARDRAIL_BASE_URL:}
    api-key: ${APPFORGE_GUARDRAIL_API_KEY:}
    model-name: ${APPFORGE_GUARDRAIL_MODEL_NAME:}
```

`semantic-enabled: false` 是明确的“仅本地检查”模式，不能声称具备语义检测能力。独立审核模型应支持 OpenAI Chat Completions 格式及 `json_object` 输出；审核提示词明确包含 JSON 约束。

## 反馈与审计

错误码 `40010` 表示输入被护轨拦截，`50310` 表示审核服务不可用；形状/长度错误继续使用 `40000`。错误中仅返回受控说明，不转发模型错误响应、内部堆栈或被拦截原文。

通过前端的参考编号，在后端 `APPFORGE_GUARDRAIL_AUDIT` 日志中搜索同一 `requestId`，可定位用户、规则和处理结果。日志可以接入现有日志收集系统；本次采用图片允许的日志方案，无需新增数据库表。部署时由日志平台配置访问权限、留存和轮转。

审计日志不保存完整提示词、完整模型回复、密钥或附件原文；新生成的聊天消息仅保存处理后的正文。原有上传附件仍归用户所有，本次不会改写或删除用户文件。

## 验证与边界

自动化验证使用本地测试模型和本地 HTTP 服务，不连接用户模型账号，不消耗付费模型额度。覆盖正常需求、隐晦风险的模拟审核结果、凭据脱敏、附件/元素上下文、重写复审、无效响应、超时、取消、SDK 和 SSE 错误、创建应用以及三种生成模式。

语义识别准确率取决于实际选用的审核模型，需要使用自己的合规样本和对抗样本联调。本次不是对任意提示词攻击的绝对安全保证；图片中未要求的输出审核、图片识别、存量历史清洗和模糊的第 2 项没有擅自加入。

本地验证结果：后端共 190 项，0 失败、0 错误，1 项需要外部构建产物的测试按条件跳过；前端 40 项测试、类型检查、生产构建及修改文件的 ESLint 检查通过。实际浏览器在 1440px 与 390px 下验证了安全检查提示、拦截说明、审计编号及错误后不自动重连。
